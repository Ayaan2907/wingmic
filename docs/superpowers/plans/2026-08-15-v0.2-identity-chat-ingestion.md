## 0 · North star for this slice

You meet someone. You talk. Then — in the same thread, without leaving it — you drop
whatever proof of them you happen to have: a photo of their badge, their LinkedIn QR,
a pasted profile link, a number they texted you. wingmic turns that into a person in
your graph, bound to the memo you just recorded, without you typing a field.

Ingestion stops being a separate screen and becomes a thing the chat absorbs.

## 2 · What LinkedIn can and cannot give

Evidence, so this is not re-litigated every sprint.

**Sign In with LinkedIn (OIDC)** grants `openid`, `profile`, `email` — name, picture, email,
and the member id (`sub`). Plus `w_member_social` for posting. That is the entire
self-serve surface. The connections API was withdrawn in 2015.

**Scraping does not close the gap:**

- Logged-out browsing hits an authwall after 2–3 profiles.
- Datacenter IPs are flagged on sight — ~99% of real traffic is residential. Getting past
  that needs residential proxies plus logged-in accounts.
- **Email is not rendered on a profile page.** It lives in Contact Info, visible only to
  1st-degree connections, and only ~30% of members permit even that. Under 10% at 2nd/3rd degree.

**Precedent:** hiQ won the CFAA point and then lost on breach of contract (Nov 2022) —
$500k judgment, permanent injunction, ordered to destroy code and data. Proxycurl, at $10M
ARR, was sued by LinkedIn/Microsoft in Jan 2025 and shut down 4 Jul 2025 under a permanent
injunction. The CFAA angle survives; the contract angle is what kills, and LinkedIn wins it.

**What a LinkedIn QR code actually encodes:** the profile URL. That URL is the same value
`matchContacts.byLinkedIn` already indexes and the LinkedIn CSV export already writes — so a
scanned QR dedupes against a bulk import for free. The vanity slug usually carries the name.

Net: QR gives the durable identifier; the mic gives role, company, and context; OCR gives
the card. Scraping would add nothing that the moment does not already supply.

## 4 · Chat as the ingestion surface (the new work)

### 4.1 What exists

- `ChatThread.tsx` (1168 lines) renders `ThreadMessage[]`; `ChatClient.tsx` owns state
- `classifyIntent()` in `_components/intent.ts` routes memo vs ask — pure, no LLM
- `capture.commit` persists transcript → `extractHybrid` → `commit()` → graph
- **`interaction.parentInteractionId` and `interaction.threadRootId` already exist** and are
  dormant (`docs/architecture.md` §3 lists them as forward-schema). This WP wires them.
- `clientCaptureId` + unique index already give idempotent retry

### 4.2 Attachment model

A third message kind alongside memo and ask: **attachment**. Dropped into the thread,
processed server-side, bound to the thread's active subject.

```
memo ──────────► person entity created (existing)
  │
  └─ attachment ─► extract identifiers ─► bind to that person
```

Extractors, in confidence order — all local, no network:

| Input | Extractor | Yields |
|---|---|---|
| LinkedIn QR image | QR decode → URL | profile URL (+ name from slug) |
| pasted text | regex | URL, email, E.164 phone |
| badge / business card photo | OCR | name, company, email, phone |
| event photo (banner, signage) | OCR + `extractHybrid` | event name → canonical `event` |

QR decode and OCR both run **client-side** — the image never has to leave the device for the
identifier path. That keeps the privacy story clean and matches how capture already works.

### 4.3 Follow-up binding — the mis-matching problem

The failure the user named: "he works on rust" arrives three messages after the memo that
introduced him, and binds to the wrong person or to nobody.

Rules, in order:

1. **Thread root wins.** Every message carries `threadRootId`. The candidate set is the
   entities resolved from the root memo — never the user's whole graph.
2. **Single candidate → auto-bind.** Root produced exactly one person; attach silently.
3. **Multiple candidates → ask once, inline.** A chip row, not a modal. The answer is
   remembered for the rest of the thread.
4. **Zero candidates → the attachment starts its own thread** and creates a person.
5. **Explicit reference overrides position.** A name in the follow-up that matches a root
   entity wins over recency.
6. **Threads expire.** A new memo after an idle gap (proposed: 30 min) starts a new root
   rather than accreting onto a stale subject.

Rule 6 is the one most likely to be wrong. It needs a real number from usage, not a guess —
flagged in §9.

## 5 · "Is this contact already a wingmic user?" — handle with care

The requested behaviour is: check whether the shared contact is a wingmic user; if so map to
them, if not create and save.

**The mapping half is fine. The telling half is not.** If wingmic ever indicates that a given
email or LinkedIn URL belongs to an existing user, it becomes a membership oracle: anyone can
test an address and learn whether that person is on wingmic. That is a disclosure about the
*target*, who never consented, and it is exactly the Framing B privacy failure
`docs/architecture.md` rejected.

Framing D already carries the machinery: `identity_claim` (with `public`), `entity_resolution`
(with `mutualConsentTs`), and `connection_request`.

**Rule:** resolve server-side, store the candidate link, reveal nothing.

```
attachment identifier
   → match against identity_claim
       → hit  → write entity_resolution (candidate, unconfirmed)
                UI shows nothing different
                both sides see it only after mutual consent
       → miss → create a private entity, as today
```

The user still gets what they want — when both people are on wingmic and both opt in, the
link is already computed and lights up instantly. What they do not get is a way to probe
membership, which is the part that would be a breach.

## 9 · Open questions — need a human call

1. **Thread expiry window.** §4.3 rule 6 proposes 30 minutes. Guess, not a measurement.
2. **OCR engine.** Client-side WASM (Tesseract — heavy bundle) vs a vision model call
   (per-image cost, image leaves the device). Affects the §4.2 privacy claim directly.
3. **Image storage.** No blob store exists today — `audioStorageKey` is dormant and unwired.
   Do attachment images persist at all, or do we extract and discard? Discarding is cheaper,
   more private, and irreversible.
4. **Gmail contacts.** Named in the ask, not scoped here. Google People API needs OAuth
   verification review — own issue, own timeline.
5. **Event photo → event matching.** Confidence is low; an OCR'd banner is weak evidence.
   Confirm-before-attach, or attach silently and allow undo?

## 10 · Out of scope

- Any LinkedIn automation: headless browsers, extensions, vendor APIs (L2)
- Pushing contacts *out* of wingmic
- Google Calendar OAuth — ICS only for now (L6)
- Revealing membership in any surface (L7)
